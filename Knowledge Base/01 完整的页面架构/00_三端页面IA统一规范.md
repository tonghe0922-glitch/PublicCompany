# 三端页面 IA 统一规范

## 1. 目的

本文件用于把 Knowledge Base 的六份页面架构表与当前 Vue 三端工程建立**唯一可追溯关系**，解决以下问题：

- 中文页面名称与代码路由没有稳定映射；
- `技术端 / 技术后台端 / admin / tech-web` 多种叫法混用；
- AI 可能根据页面标题自行创造 route、permission 或 process；
- 三端复制同一业务页面时无法判断谁是事实源；
- 移动端菜单可能只做“显示入口”，未验证完整可达。

本文件只统一**命名、追溯字段与治理规则**，不修改六份 Excel 中已批准的业务页面内容。

## 4. 三端唯一编码

| portal_code | 中文 | runtime_portal | 当前代码目录 |
|---|---|---|---|
| `employee` | 员工端 | `employee` | `technical-platform/web/src/portals/employee` |
| `center` | 中心管理端 | `center` | `technical-platform/web/src/portals/center` |
| `tech` | 技术后台端 | `admin` | `technical-platform/web/src/portals/admin` |

### 强制规则

- 文档、Knowledge Base 派生目录、权限矩阵统一使用 `tech`；
- 当前运行构建仍可使用 `admin`；
- `admin` 不得产生一个新的业务端口；
- 禁止再定义 `manager`、`backend`、`superadmin` 等平行 portal_code；
- “中心管理员”属于角色，不是第四个门户；
- “系统管理员”属于技术端角色，不是业务事实超级权限。

## 6. 页面名称规则

### 6.1 中文展示名称

- 优先沿用 Knowledge Base；
- 不能因为代码文件名更短就改业务名称；
- 不能出现同一业务：
  - “审批中心”
  - “审核中心”
  - “待办审批”
  三种没有映射的平行名称。

如确需别名，保留：
```text
canonical display_name
aliases[]
```

### 6.2 route_name

推荐稳定英文：
```text
employee-home
employee-expense-claims
center-finance-expense-review
tech-event-dead-letter
```

route_name：
- 不含中文；
- 不使用临时编号；
- 不把角色名硬编码为业务事实；
- 变更需要兼容/跳转策略。

### 6.3 route_path

URL 表达资源/页面，不表达权限结论。

禁止：
```text
/admin/all-data
/admin/super-finance
```

推荐语义：
```text
/employee/...
/center/...
/admin/...    # 当前 runtime alias，可在后续 ADR 改为 /tech
```

## 7. permission_code 映射

权限码不是页面名自动转换。

规则：
1. 先查 canonical IAM permission；
2. 页面可以组合多个 permission；
3. 一个页面可见 ≠ 所有动作可执行；
4. `view / create / submit / approve / export / reveal-sensitive` 分开；
5. 前端只做显示；
6. API 再校验；
7. DB/RLS 再限制行。

禁止：
- 因页面叫“财务中心”就给 `FINANCE_ALL`；
- 因技术端叫 admin 就获得所有业务 permission。

---

## 8. process_code 映射

业务页面必须关联 P001–P126。

允许：
- 一个页面关联多个流程；
- 一个流程在三端有不同页面；
- 平台技术页可标为 `PLATFORM`，同时关联 P089/P091/P092/P093/P094/P126 等治理流程。

禁止：
- 业务页面没有 process_code；
- 仅以“模块名称”代替流程；
- 三端为同一流程各建一份独立业务事实。

---

## 9. 三端同一流程的页面关系

例如 P025 报销：

```text
employee:
  发起/草稿/凭证/提交/本人结果

center:
  费用校验/审批/财务登记/归档办理

tech:
  event/接口/outbox/retry/dlq/审计技术视图
```

三个页面可完全不同，但：
- claimId 相同；
- processInstance 相同；
- 状态事实相同；
- tech 不产生业务批准事实。

## 10. 首页规则

首页不是第二份业务数据库。

首页卡片必须来自：
- 查询/读模型；
- 待办；
- KPI；
- 服务端 projection。

首页不得：
- 自己保存一份“审批状态”；
- 用本地 mock 作为生产事实；
- 直接修改业务状态。

---

## 11. 移动端

`mobile_access`：

### full
完整闭环可办理。

### limited
只读或安全限制下的部分操作，但必须有明确 PC/人工继续入口。

### no
确因技术/安全不允许，但不得导致员工核心义务无法完成。

员工端核心流程原则上应 full 或有可完成替代路径。

## 12. Implementation Mapping

### 当前入口

```text
technical-platform/web/src/main.ts
  employee -> ./portals/employee/main
  center   -> ./portals/center/main
  admin    -> ./portals/admin/main
```

### 构建

```text
pnpm build:employee
pnpm build:center
pnpm build:admin
```

### 注意

根 `src/router.ts` 目前仍包含 legacy 入口，不应被误认为三端正式 IA 的唯一 Router。  
三端现有实现由 portal entry 组合；后续页面路由治理必须先确认真实入口，不得只看 legacy router。

## 13. 页面实现完成定义

一个页面只有同时满足才算 implemented：

- 来源可追溯；
- portal_code 正确；
- route 稳定；
- permission 映射；
- process 映射；
- 数据范围；
- L3/L4；
- loading/empty/error/no-permission；
- PC；
- mobile；
- API 后端权限；
- 可访问性；
- 回归测试；
- 不复制事实。

---

## 14. 变更流程

新增/删除/改名页面：

1. 修改批准的 Knowledge Base 页面架构；
2. 更新来源 hash；
3. 更新 page catalog；
4. 更新 route/menu；
5. 更新 permission；
6. 更新 process mapping；
7. 更新 E2E；
8. 必要时 ADR；
9. 页面下线保留 redirect/deprecation；
10. 不直接删导致收藏/通知链接失效。
